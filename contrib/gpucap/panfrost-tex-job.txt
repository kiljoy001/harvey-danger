Textured draw capture (G52, Mesa 25.0.7)
========================================

contrib/gpucap/capture_tex.c: 64x64 RGBA8 FBO, a 2x2 RGBA8 source texture
(red, green / blue, white), NEAREST/CLAMP, one attribute (a vec4 position),
UVs derived in the vertex shader, full-screen triangle.

  EGL_PLATFORM=surfaceless PAN_MESA_DEBUG=trace,linear,nocrc,dump /capture_tex
  TEX pixel ff0000ff

so the bottom-left texel (red) was sampled.

What a textured draw adds over the plain one
--------------------------------------------
Mesa used IDVS: a *primary* vertex shader (position only) plus a *secondary*
one that also writes the UV varying, chosen per primitive.

  vertex primary    GPU VA a003000   position only, ST_CVT.v4
  vertex secondary  GPU VA a0030c0   position + attribute 1 -> ST_CVT.v2
  fragment          GPU VA a00318 0  ATEST + BLEND, no explicit LD_TEX

Vertex renderer state:
  Attribute count 1, Varying count 2, Uniform buffer count 1,
  Secondary shader 0xa0030c0, Secondary preload uniform count 3
Tiler job payload: Primitive Secondary Shader = true

Varyings (vertex job):
  Varying 0: buffer 1, Snap 4 RGBA      (position, 16 bytes)
  Varying 1: buffer 0, RG16F RGB1       (uv, 4 bytes)
Varying buffers @0xa00a2e0:
  [0] pointer 0xa01a000  stride 4   size 12
  [1] pointer 0xa01a040  stride 16  size 48

Fragment renderer state:
  Sampler count 1, Texture count 1, Varying count 1
  Message preload 1: VAR_TEX, varying 0, texture 0, register format F16
  (the sample is issued by the preloaded message; the shader body is only
   ATEST + BLEND, using r1 which the preload filled)

Fragment draw:
  Textures 0xa00a200, Samplers 0xa00a220, State 0xa00a280,
  Viewport 0xa00a120, Varyings 0xa002060, Varying buffers 0xa00a2e0,
  Position 0xa01a040, Thread Storage 0xa00a100

Texture descriptor @0xa00a200
  Type 2, Dimension 2D, Format RGBA8 UNORM, Width 2, Height 2,
  Swizzle 1672 (RGBA), Texel ordering Linear, Levels 1,
  Minimum level 0, Min/Max LOD 0, Sample count 1, Array size 1, Depth 1,
  Surfaces -> 0xa002040

Surface With Stride @0xa002040
  Pointer 0xa004000, Row stride 64, Surface stride 128
  (a 2x2 RGBA8 is 8 bytes of data; the strides are the aligned ones Mesa
   uses for linear textures, not width*4.)

Sampler descriptor @0xa00a220
  Type 1, Wrap R Repeat, Wrap S/T Clamp to Edge,
  Round to nearest even, Normalized coordinates, Seamless cube map,
  Clamp integer array indices, Minify/Magnify nearest,
  Mipmap mode None, Min LOD 0, Max LOD 31.996094, LOD bias 0,
  Max anisotropy 1, LOD algorithm Isotropic, Compare function Never,
  Border colour 0

Implications for gpufs
----------------------
* One attribute is enough if the UV is derived from the position, and that
  avoids IDVS entirely: no secondary shader, no `Secondary Shader` bit, and
  attribute count stays 1.  That is the cheap path for a blit.
* The sample can arrive as a *message preload* rather than instructions, and
  the fragment renderer state has to carry it.  `pan_shader_prepare_rsd`
  fills the message preloads from `pan_shader_info`, so gpucc gets this for
  free provided the shader really uses a texture.
* A texture is a descriptor pointing at a surface-with-stride, so the blit
  needs: one texture descriptor, one sampler descriptor, and a surface that
  describes the client's buffer (pointer, row stride, surface stride).
* `Row stride` and `Surface stride` are not `width*4`; the texture path has
  its own alignment.  For a scanout-shaped buffer both should be the real
  stride, which is what the blit will use.
