Vendor Mali userspace field names
=================================

Source
------
`libmali-bifrost-g52-g24p0-gbm.so` from the Rockchip libmali mirror
(https://github.com/JeffyCN/mirrors, branch `libmali`,
`lib/aarch64-linux-gnu/`).  The mirror's `gpu-chips.txt` maps
`bifrost-g52: rk3566_rk3568 rk3562 rk3576`, so this is the right family for
the Orange Pi 3B.

  libmali-bifrost-g52-g24p0-gbm.so       56287608 bytes
    sha256 bc6be2fd5d8b46bb9d4cb22118a3ff77af1ca46cee1ac12bc78e27f89ba3ea3d
  libmali-bifrost-g52-g24p0-nocl-dummy-gbm.so  22854672 bytes
    sha256 96d029f9411ba102c9bdfb2e3191e9d7a1bc03525ba2a6dddc34288eb220514e

Both are stripped aarch64 shared objects, 16 MB of `.text`.  They carry a
table of debug field names in `.rodata` plus a pointer table in `.data`
(RELATIVE relocations in `.rela.dyn`) that names the fields of the job
manager structures.

Tiler context (`.rodata` 0x1125d60, in vendor order)
----------------------------------------------------
    polygon_list
    level_mask_and_sample_pattern
    frame_buffer_width_height
    reserved_1
    heap_descriptor_pointer
    tile_weight
    reserved_2
    private_state

That is the `TILER_CONTEXT` in `contrib/gpucap/panfrost-draw-job.txt`, field
for field and in the same order:

    offset 0x00  polygon_list                    (64-bit)
    offset 0x08  level_mask + sample_pattern     (13 + 3 bits)
    offset 0x0c  fb_width / fb_height            (16 + 16)
    offset 0x10  reserved_1
    offset 0x18  heap_descriptor_pointer
    offset 0x20  tile_weight
    offset 0x28  reserved_2
    offset 0x30  private_state

Tiler heap
----------
    heap_size
    heap_pointer
    low_pointer
    high_pointer

which is the four 64-bit fields of `TILER_HEAP` we write as
`size / base / bottom / top` -- the vendor's `low_pointer`/`high_pointer` are
the ones that advance as the hardware allocates chunks.

Nearby names in the same table, for orientation:

    cdsbp_0, _ssbo0, _ssbo1, _ssbo2, gpu_hd, gpu_td, src_td
    mem_region, jit_memory_region, base_address, size_in_bytes, used_bytes
    pages_to_initially_commit, pages_to_grow_on_page_fault, error_flag_address
    first_tiler_job_address, tiler_job_array_address, tiler_job_address

and the kbase event names (`JOB_CONFIG_FAULT`, `BASE_JD_EVENT_JOB_INVALID`, ...)
which match the exception table in the kernel module.

What this settles
-----------------
* The tiler context layout `gpufs` builds from the capture is the vendor's
  layout, independently of Mesa.
* `heap_descriptor_pointer` really is a pointer to the heap descriptor (our
  FBD "Tiler" field points at the context which points at the heap), and
  `bottom`/`top` are the heap's low/high pointers.
* Nothing else in the descriptor set needed correcting: the draw already
  runs.

REA notes
---------
REA (Ghidra 12.1.4) will not import these blobs: 16 MB of `.text` exceeds the
330 s provider gap, and only the data-only extract is stable:

    llvm-objcopy --only-section=.rodata --only-section=.dynstr \
        --only-section=.data.rel.ro --only-section=.data in out
    # REA opens it: 12 segments, 0 procedures, 26373 strings

So the field names above were recovered from the string/pointer tables
directly; REA is the tool for the small vendor `kbase` module, not for a
16 MB GLES driver.

Slicing it for REA
------------------
`.text` is 16 MB, which no Ghidra import survives (330 s provider gap).  A
4 MB slice with `.rodata`/`.data`/`.dynsym` left at their real addresses does
import, and `contrib/gpucap/mkslice.py` builds one:

    python3 mkslice.py 0x12aa00 0x400000 sA.elf

(Slice 0 imports in ~82 s and analyses 9,175 procedures.  Slice N covers
`0x12aa00 + N*0x400000`.)

What the slices show
--------------------
`glDrawArrays` is a thin wrapper:

    ctx = tpidr_el0[0];                     // cached context
    *(u32 *)(ctx + 0x48) = 0x90;            // call id
    if (profiling) { ...; FUN_003ddf80(buf, &record, 0x28); }
    else FUN_00292a60(ctx, mode, first, count);
      -> FUN_002f9c00(ctx, mode, first, count, ...)   // draw dispatcher

`FUN_003ddf80` allocates a record with a 16-byte header inside a 0x3ff0-byte
buffer (`0x3ff0 - used`), growing it through a vtable at
`ctx->hal[0x18/0x20/0x28]`.  That is a kbase **atom/trace buffer**, not a job
chain builder: libmali is a kbase *client*.  It builds atoms and submits them
with ioctls; it never touches `JS_CONFIG`, the MMU or the job slots.  So this
blob cannot answer register-level questions -- only the descriptor/atom
layout, which the Mesa capture already gives us.

Tiler heap ownership
--------------------
The vendor kbase UAPI has no JM tiler heap manager.  The only kernel reach
into it is `base_jd_replay_payload.tiler_heap_free`
(`drivers/gpu/arm/midgard/mali_base_kernel.h`), which the kernel advances
after replaying a faulted frame.  Everything else is userspace's: the same
conclusion as Mesa's `jm_emit_tiler_desc`, which hands over
`size/base/bottom/top` with `bottom == base` and lets the hardware write the
first chunk and the polygon list.  `gpufs` does exactly that (4 MiB heap,
zeroed, `polygon_list = 0`) and the draw runs, which is the empirical
confirmation.
