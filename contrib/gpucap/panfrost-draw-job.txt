Captured on the Orange Pi 3B (RK3566, Mali-G52) by booting the Armbian
6.18.21 kernel plus a Debian arm64 initramfs over TFTP and running
contrib/gpucap/capture_draw.c: a 64x64 RGBA8 FBO, cleared to blue, then one
full-screen triangle with

  vertex    gl_Position = position;            (attribute 0, vec4)
  fragment  colour = vec4(1,0,0,1);

  EGL_PLATFORM=surfaceless PAN_MESA_DEBUG=trace,linear,nocrc,dump /capture_draw

  DRAW pixel ff0000ff

so the draw landed.  Mesa 25.0.7, panfrost 1.4.0.

This is the reference for the shader path: unlike a clear, it needs a tiler
job, shader program descriptors, attribute state, a tiler context and a
tiler heap.  The dump below is from `PAN_MESA_DEBUG=...dump`, which hexdumps
every graphics buffer, so the bytes are exact.

---- what this means for gpufs ----

The clear needs none of this: no tiler job, no shaders, no heap.  A draw
needs all of it, and the descriptor set is what the Gallium driver builds
at draw time.  The pieces to reproduce, in order of risk:

1. SHADER_PROGRAM for each stage from the gpucc blob plus pan_shader_info.
2. RENDERER_STATE (the "State:" block above) and the fragment blend state.
3. Attribute buffer / attribute descriptors for attribute 0.
4. Thread storage (TLS) descriptor; TLS size is 0 for both stages here.
5. Tiler context + tiler heap + polygon list tag.
6. TILER job payload (invocation, primitive, primitive size) and the
   VERTEX/FRAGMENT job chain with Next patched.

The tiler heap is a 128 MiB VA range based at 0x2000000 in this capture,
but only the first pages are touched; a much smaller heap is fine as long
as the polygon list tag, base, bottom and top are consistent.
