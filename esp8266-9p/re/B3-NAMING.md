# B3 - ROM names, SDK fingerprint naming, MMIO attribution, structs

Continues B2. B0/B1/B2 reports, the backup, and extracted images are
unchanged. Offline only; the board was not touched. New inputs this
stage are external: the pinned NONOS SDK 2.0.0 (see `sdk/PROVENANCE.md`
for source, commit, and hashes - read that caveat before trusting any
SDK-derived name below).

## 1. ROM targets: all 76 named

`scripts/rom_map.py` joins B2's `external-calls.csv` with
`PROVIDE` lines in the SDK's `ld/eagle.rom.addr.v6.ld`. Result:
**76 of 76 targets named, 0 unnamed** (`inventory/b3/rom-targets.csv`).
The B2 hypothesis about the hot cluster was right in shape and is now
proven by the vendor map, not by caller-context guessing:

- 0x400018b4 `ets_memcpy` (576 refs / 280 callers)
- 0x400018a4 `ets_memset` (184/127), 0x400018d4 `ets_memcmp` (166/99)
- 0x40002ac8 `ets_strlen` (131/54), 0x40002ae8 `ets_bzero` (94/63)
- 0x400024cc `ets_printf` (93/53), 0x4000e21c `__udivsi3` (85/58)
- 0x40000f74 `ets_intr_lock` (69/45), 0x40000f80 `ets_intr_unlock` (73/43)
- 0x40000e24 `ets_post` (32/28) - note: different address from the
  IRAM alloc wrapper at 0x40100e24 named in B2; the similarity is
  coincidence and the two must not be conflated.
- Also present: `ets_delay_us`, `ets_task`, `ets_isr_attach/mask/
  unmask`, `gpio_output_set`, `Wait_SPI_Idle`, `SPIRead`,
  `Cache_Read_Disable/Enable`, `uart_div_modify`, `sha1_prf`,
  `lldesc_build_chain` (DMA descriptor builder - a B4 lead for the
  wdev replacement), and the compiler runtime (`__divsi3`,
  `__muldi3`, float helpers).

For the blob-free build (DESIGN 6.1 stage B4) this list is the ROM
contract: these 76 are what our code may keep calling (mask ROM is
hardware), and everything else the blobs use is now enumerable.

## 2. SDK fingerprint naming: 33 functions renamed

`scripts/lib_symbols.py` extracts symbol tables from the SDK `.a`
files with a stdlib ar/ELF parser (the libraries are stripped of
locals too - only globals are recoverable this way).
`scripts/fingerprint.py` then matches each global function by
sampling 24-byte code windows from the SDK object and searching them
in the extracted image segments - byte evidence, independent of
Ghidra's boundaries. Of 101 sampled Wi-Fi functions: **32 strong
matches (>=3 agreeing windows), 26 weak (1-2), 43 no match**.
The no-match set is consistent with the provenance caveat: the
board's image was compiled 2016-08-09, before the v2.0.0 tag.

33 renames were applied to the Ghidra project by the generated
`scripts/B3Rename.java` (32 strong + `wifi_mode_set` by exact size
469 + anchor + behaviour triangulation). Strong matches include
`hostap_input` (11/74 windows; its Ghidra entry was not found, so it
is recorded in the CSV but not yet renamed), `ieee80211_parse_beacon`
(44/74), `sta_input` (24/55), `ieee80211_send_mgmt`,
`ieee80211_beacon_alloc`, `scan_parse_beacon`, and on the libpp side
`wDev_AppendRxBlocks`, `wDev_SetBssid` (11/12), `wDev_SetMacAddress`,
`wDev_Insert_KeyEntry`, `wdev_go_sniffer` / `wdev_exit_sniffer`.
Full table: `inventory/b3/fingerprints.csv`.

Two conflicts with B2 candidate names, stated plainly:

- 0x40220fac: B2's `ieee80211_opmode_setup` is SDK `wifi_mode_set`
  (exact size 469, mode switch + MAC print behaviour). Renamed;
  the SDK name wins.
- 0x40221810: B2's `hostap_teardown` vs SDK `ieee80211_hostap_attach`
  (size 203 vs Ghidra's 202). The byte fingerprint for attach found
  **0 matching windows**, and the decompiled body only frees
  structures. The SDK name was applied on size+anchor evidence, but
  the conflict is **unresolved**: this may be a local detach helper
  merged into the Ghidra function, or attach in this build really
  does start as pure teardown. Do not trust either name for this
  address yet.

`scripts/B3Rename.java` is generated by `apply_fingerprints.py`;
regenerate it rather than editing it by hand.

## 3. MMIO attribution

Per-register referrers (with current function names) are in
`inventory/b3/mmio-registers.csv` (scripts/B3Dump.java). Banks:

- **0x3ff20000 WDEV/MAC: 82 addresses, 384 refs.** No public register
  names exist (eagle_soc.h does not cover WDEV), so attribution is
  by named referrer, which now works:
  - 0x3ff20c3c / 0x3ff20c44 - written by `wDev_SetBssid` (BSSID MAC
    registers; two words of the address).
  - 0x3ff20c5c area - referenced by `wDev_SetMacAddress` and the
    Enable/DisableUcRx pair (own-MAC registers).
  - 0x3ff20800 / 0x3ff20804 - referenced by `wdev_go_sniffer`,
    `wdev_exit_sniffer`, `wDev_Crypto_Conf`, and two neighbours at
    0x40220664/0x402206b8 (RX-mode/filter control pair).
  - 0x3ff2006c - hottest WDEV register (50 refs), touched by
    sniffer, option-init and many IROM paths; a central control/
    status register, exact role open.
  - 0x3ff20c00 (54 refs) and 0x3ff20c74 (24) - heavy use from IRAM
    system functions (0x40101ac0, 0x40103728, 0x4021ab40 cluster);
    roles open.
- **0x60000000 peripherals: 144 addresses, 893 refs.** Publicly
  named by eagle_soc.h where the SDK covers them: DPORT-adjacent
  work is at 0x3ff00000 (below); within 0x60000xxx the header names
  GPIO 0x60000300, TIMER 0x60000600, RTC 0x60000700 (35 addrs /
  159 refs - the single biggest sub-bank, mostly sleep/timing),
  IO_MUX 0x60000800. UART0 at 0x60000000 (28 refs to +0x0c from the
  uart.c functions). Sub-banks at 0x60000200 (120 refs, IRAM system
  functions), 0x60000500, 0x60000d00, 0x60001100 and 0x60009800-
  0x60009d00 (baseband-adjacent, ~100 refs) have **no public names**
  and are recorded by address and referrer only.
- **0x3ff00000 DPORT: 13 addresses, 101 refs.** Hottest +0x14
  (28 refs) and +0x18 (21); eagle_soc.h names +0x04 as
  EDGE_INT_ENABLE_REG; the rest are unnamed in public headers.

Load/store direction and access width were still not split; a
register called a "control register" above means "written by the
named setter function", which is the evidence actually in hand.

## 4. Shared global structs (first reconstruction)

- **`g_ic` (ieee80211 state).** SDK `ieee80211.o` has a global
  OBJECT `g_ic`, size **1704 bytes**, in .bss. In the image, code
  reaches the central struct through the literal cell at
  0x4020101c, whose value is **0x3fff06d4** - BSS just past the
  loaded DRAM segment, consistent with `g_ic`'s linked address.
  Confidence: high that 0x3fff06d4 is `g_ic` (size and centrality
  corroborate; no symbol table in the image to prove it directly).
- Field evidence so far (offsets from that base, from decompiled
  `wifi_mode_set` and the hostap teardown path):
  - +0x10: pointer, allocated 0x2a0 (688) bytes during mode setup.
  - +0x14: pointer to the softc/hostap context struct. Its fields:
    +0x50 flags word (bit 0x10 cleared on teardown), +0x54 byte
    zeroed on teardown, +0x98 pointer (whose +0x08 is zeroed),
    +0xcc pointer to the AP struct. The AP struct chain continues:
    *(ap+0x18) -> struct with +0x00, +0x50 freed in teardown;
    *(ap+0x04) -> struct with +0x38, +0x3c freed in teardown.
    Free line numbers in the SDK-named path (0x1ab-0x1c3) give the
    teardown order.
  - +0x130: pointer freed by `regdomain_free_field130` - but the
    argument struct of that helper is not yet proven to be `g_ic`
    itself, so +0x130 is recorded as "field of the regdomain
    helper's struct", not yet as a `g_ic` field.
- A second global pointer cell, *0x402056d0 = 0x3ffeacf4 (just past
  the loaded DRAM segment), supplies the MAC bytes printed by
  `wifi_mode_set` at offsets +0x1e..+0x23 of its struct. Identity
  open - likely the station/netif info block.

This is a skeleton, not a layout: most of the 1704 bytes are still
unattributed. The fastest route to more fields is decompiling the
now-named functions (`sta_input`, `hostap_input` once located,
`ieee80211_send_mgmt`) and harvesting their base+offset accesses
against the same two bases.
