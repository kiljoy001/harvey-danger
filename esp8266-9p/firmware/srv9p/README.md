# srv9p - 9P2000 server core for the plan9ized firmware

Transport-agnostic implementation of DESIGN section 4.3 over
the frozen namespace (DESIGN section 5). One client, 16 fids,
msize 2048, static message buffers plus one pp_arena mark per
message (PLAN9-OS section 4.5: transient parse/scratch space is
released by rewind after every reply).

- `srv9p.h` / `srv9p.c` - protocol, fids, walk/stat/read/write.
  The application supplies a file table (path, qid, dir,
  writable, read/write callbacks). Directories are generated by
  the core as stat entries.
- `test/srv9p_host.c` - host harness: the frozen namespace with
  mock state over a POSIX socket, for testing the exact core
  that will run on the chip.

Verification (three independent implementations agreeing):

- Go mock (mock9p) + independent Python 9P2000 client: pass.
- This C core in the host harness + the same Python client
  (version, attach, listing, nested walk, stat, ctl acceptance
  and bad-verb rejection, bad-walk rejection): pass.
- Xtensa cross-build under -Wall -Wextra -Werror: clean
  (pp9_init, pp9_serve).

Host test commands:

    cc -std=c99 -Wall -Wextra -Werror -o /tmp/srv9p_host \
      srv9p.c ../libpp/pp_arena.c test/srv9p_host.c
    /tmp/srv9p_host 1565   # then run a 9P client against it

Next integration (Phase A): an ESP8266 app supplies the real

sockets); IL transport reuses this core unchanged, since the
